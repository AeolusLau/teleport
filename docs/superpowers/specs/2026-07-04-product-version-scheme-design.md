# 设计:产品版本方案——构建期以 TELEPORT_VERSION 替换 chrome/VERSION(TD-014 根治)

- 日期:2026-07-04
- 状态:已评审(方案 A + 四段版本统一,用户已确认)
- 关联:`docs/tech-debt.md` TD-014(本设计实现后结清)、commit `f5dcd8f`(症状点修复:CFBundleGetInfoString / SCMRevision)

## 1. 背景与目标

TD-014 审计确认:分发包内多处暴露 Chromium 版本号 `148.0.7778.180`——框架 versioned 目录名(`Teleport Framework.framework/Versions/148.0.7778.180/`,与主 exe 的 `dlopen` 编译期常量 `CHROME_VERSION_STRING` 硬耦合,`chrome/app/chrome_exe_main_mac.cc:182`)、4 个 Helper 与 Framework 及 app_mode 模板的 plist 版本键、二进制内嵌路径/UA 常量。打包期无法修(改目录名必然启动失败),根治必须在构建期。

**目标**:

1. 分发包内一切可检视的版本信息(目录名、全部 plist、`CHROME_VERSION_STRING` 派生物、DM 上报)只呈现**产品版本**;
2. web 兼容性指纹(UA / UA-CH)**保持引擎版本**,与今天完全一致;
3. 版本形态全链路唯一:一个字面值贯穿 About、dmg、tag、appcast、磁盘布局;
4. 升 chromium 基线时不需要重新审计暴露点(机制自动跟随)。

**非目标(YAGNI)**:不隐藏 UA major(web 兼容依赖,业界含 Brave 均不隐藏);不处理未启用的 PWA app shim 旧路径迁移;不做 Sparkle 跨版本形态的比较兼容(见 §2 决策 4)。

## 3. 版本事实源与生成机制

两个事实源,各司其职,均为仓库既有文件:

- **`TELEPORT_VERSION`**(升级为四段,如 `0.1.8.0`)→ 产品版本,驱动一切「我们是谁」。
- **`CHROMIUM_VERSION`**(`148.0.7778.180`,钉死上游基线)→ 引擎版本,只驱动 UA/UA-CH。

`apply_patches.py` 新增一个 transform 步骤(与 `branding_strings` 同类,幂等重写):

1. **生成 `chrome/VERSION`**:读 `TELEPORT_VERSION` 四段,直写检出 `chrome/VERSION` 的 `MAJOR=/MINOR=/BUILD=/PATCH=` 四行。**现场生成而非静态 patch**——内容随每次发版变化,静态 patch 每次 bump 都需 regenerate,现场生成才守住单一事实源。升基线时 `gclient sync` 把该文件还原为新上游值,重跑 `apply_patches.py` 即覆盖,自愈。
2. **生成引擎版本头** `components/version_info/teleport_engine_version.h`(检出内 **untracked** 文件):

   ```c
   // Generated by apply_patches.py from CHROMIUM_VERSION. Do not edit.
   #define TELEPORT_ENGINE_VERSION_STRING "148.0.7778.180"
   #define TELEPORT_ENGINE_VERSION_MAJOR "148"
   ```

   放 `components/version_info/` 是因为三个 UA 组装点分别在 `components/version_info/` 本地与 `components/embedder_support/`(后者已依赖前者,include 层级干净)。untracked 文件被 `git clean`/sync 清除也无妨——工作流本就要求 sync 后重跑 apply_patches;文件缺失时引用它的 patch 编译即失败,fail-fast。

由此自动变为产品版本、零枚举:`CHROME_VERSION_STRING` 及其全部派生物(框架 `Versions/X.Y.Z.W/` 目录名、主 exe dlopen 内嵌路径)、全部 plist 版本键(主 app、4 个 Helper、Framework、app_mode 模板)、`CFBundleGetInfoString` 若显示版本(已去版本化,双保险)、`version_info::GetVersionNumber()` 全部消费方(About、DM `browser_version`、崩溃标注等)。

## 4. UA / UA-CH:引擎版本 patch 面(闭合三点,已逐一源码确认)

| Patch 点 | 现状(替换后若不动) | 改为 |
|---|---|---|
| `components/version_info/version_info_with_user_agent.cc` `GetProductNameAndVersionForReducedUserAgent()` | `"Chrome/" + 产品 major + ".0.0.0"` → `Chrome/0.0.0.0`,web 兼容崩坏 | `TELEPORT_ENGINE_VERSION_MAJOR` → `Chrome/148.0.0.0` |
| `components/version_info/version_info_with_user_agent.h` `GetProductNameAndVersionForUserAgent()`(constexpr `"Chrome/" PRODUCT_VERSION`) | 产品全版本(UA reduction 被策略关闭时的完整 UA) | `"Chrome/" TELEPORT_ENGINE_VERSION_STRING` |

## 5. 展示层:`teleport_version` 重构

现行 dev 判定启发式(`ResolveDisplayVersion`:plist 版本 == Chromium 版本 ⇒ 未 stamp ⇒ `0.0.0-dev`)在替换后恒相等、失效。重构为**编译期判定**:

- 显示值 = `version_info` 产品版本四段原样(如 `0.1.8.0`);
- 非 official 构建(dev)显示 `X.Y.Z.W-dev`(`is_official_build` buildflag,替代运行时启发式);
- `teleport_version_mac.mm` 的 plist 读取逻辑整体删除(mac 特例不再需要),`ResolveDisplayVersion` 删除;单测按 TDD 重写。

## 6. 打包与发布链

- **删除 `_package.py` 的版本 stamp**(plutil 改写 `CFBundleVersion`/`CFBundleShortVersionString`):构建期烘焙值即正确产品版本。
- **新增打包前一致性断言**:产物 `CFBundleShortVersionString` == `TELEPORT_VERSION` 内容,不等则拒绝打包——抓「bump 版本后忘跑 apply_patches / 误拿旧构建打包」。
- **新增 patch:`build/apple/tweak_info_plist.py`**,mac 分支 `CFBundleVersion` 由上游 `BUILD.PATCH` 两段改为完整四段。上游行为对我们是隐患:`CFBundleVersion` 是 Sparkle 比较键,`BUILD.PATCH` 在跨 minor 时非单调(`0.1.7.0→"7.0"`,`0.2.0.0→"0.0"`,升级链路断);原三段方案靠 stamp 掩蔽,现在根修。顺带 Helper 的 `CFBundleVersion` 也从 `7.0` 变 `0.1.7.0`。
- **`_release.py` 升四段**:`TELEPORT_VERSION` 解析/校验/单调比较按四段;比较对历史三段 tag(`v0.1.7`)缺位补 0,发布护栏(tag 与线上 feed 双查)对旧历史仍工作。
- dmg 名(`Teleport-0.1.8.0.dmg`)、git tag(`v0.1.8.0`)、appcast `sparkle:version`(取自烘焙 `CFBundleVersion` = 四段)自然统一。
- 已装 canary(三段 `0.1.7`):手动重分发新包(决策 4),不依赖 Sparkle 跨形态比较。

## 7. DM 上报(跨 fairyland 配对改动)

- `browser_version`(`components/enterprise/browser/reporting/browser_report_generator.cc:59` = `GetVersionNumber()`)→ 替换后自动为产品版本,客户端零 patch,管理面主显示。
- 引擎版本:patch `chrome/browser/policy/device_management_service_configuration.cc` 的 `GetAgentParameter()`(现为 `"<产品名> <版本>(<lastchange>)"`),改为 `"<产品名> <产品版本> Chromium/<引擎版本>(<lastchange>)"`(引擎值来自 §3 引擎头)。该参数随**每个** DM 请求的 `agent` query 上行(`dmserver_job_configurations.cc:194`),选它是因为是现成扩展点、零 proto 手术。
- **fairyland 侧**(同名配对 worktree/分支 + 其侧独立 spec,按 cross-repo 惯例):device-manager 在 register/status 处理时解析 `agent` 中 `Chromium/<ver>`,持久化 `engine_version` 字段,管理面设备详情双版本展示。协议面变化仅此一处,两端同批合并。

## 8. 风险与已知项

- **`MAJOR=0` 的下游假设**:按自身 major 分支行为的子系统在本产品均已死——variations/Finch 不拉种子(TD-NOTE)、组件更新器无后端(TD-002)、崩溃上报不外发(TD-NOTE);外部 Google 端点无关。V8/Blink 版本独立于 chrome/VERSION,不受影响。以冒烟兜底(§9)。实施与终审补充:除已 patch 的两处 codegen(`generate_policy_source.py`、`generate_unexpire_flags.py`)外,证实仍有三处残余——①扩展 `minimum_chrome_version` 门(`minimum_chrome_version_checker.cc` 以产品版本比对 manifest 最低 Chrome 版本,将来启用扩展 force-install 前须按 UA 同款模式 patch 为引擎版本);②flags 过期机制静默失效(`generate_expired_list.py` 以 MAJOR 为 mstone,`expired_flags_list.cc` 生成空表,chrome://flags 上游已过期实验项全部重新可用);③政策 `supported_on` 过滤退化为全量超集(`generate_policy_source.py:130` 真值判断,方向安全:只多不少)。三项登记为 TD-015。
- **PWA app shim**:versioned 路径随产品版本自洽;旧 shim 迁移场景未启用,不处理(记录在案)。
- **发版 bump 触发大范围重编**:`chrome/VERSION` 是众多目标输入,bump 后首次构建接近全量。release 本就全量;dev 极少 bump,接受。
- **检出内生成物**(`chrome/VERSION` 改写、引擎头 untracked):`git clean`/sync 后消失 → apply_patches 重跑恢复;引擎头缺失时编译 fail-fast,不会静默错版本。
